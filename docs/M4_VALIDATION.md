# M4 養成、資格與活動驗證

對應 FR-007–FR-011；AC-033–AC-049、AC-057，並回歸 AC-011／AC-012 的占用不變條件與 M1–M3 協作行為。

## 可操作的流程

- 「養成與活動」集中處理職業門檻、確認等級／任務道具／功勳、資格輪次、入場分流、活動結束、所得與兌換、重刷、永久失格及封存／接替。
- 職業門檻初始為空，使用者依實際遊戲設定。表單的 1／0／1 只作輸入起點，不宣稱是遊戲門檻。沿用既有階段 ID；任務檢查等級、功勳階段檢查等級與道具、正式活動檢查本輪資格。可調整來源階段及進入條件，沒有任意腳本引擎。
- 養成進度只記最後確認值，不要求逐日任務欄位或逐場勝負。達標時建立資格輪次，保存職業門檻、時區及換日時間快照。舊標籤不自動轉為已確認進度。
- `TimeProvider` 注入伺服器 UTC 時間。`EligibleFrom` 是工作區嚴格下一個 04:00；重複保存及後續設定修改都不重算舊輪次。進場以伺服器目前時間驗證；補填時間也必須位於可投入至目前時間之間。既有定期快照校對更新畫面資格，不靠客戶端倒數或排程判定是否可入場。
- 單卡只有一筆未結束活動。分流與實際進入時間在同一命令保存；`RecordedAt` 保留原回報時間，補填需原因及版本，日誌保存前後分流／時間。結束後再入場產生新 ID。活動操作者與卡片主要操作者分開保存，當時為 Admin 的活動身分即使日後改名仍不公開。
- 所得以增量回報；兌換量為正整數、支援部分兌換，1:1 扣可用功勳並加累積金幣。需要本輪已成功入場且未失效；可設定必須仍在活動中。兌換至 0 保留已啟用資格。累積量不記支出，校正需要最新金幣版本與原因。
- 重刷明確撤銷本輪，保留等級、道具、歷史及累積金幣；使用者填入重刷後確認的剩餘功勳，返回設定的累積階段，再次達標建立新輪次。沒有推定死亡次數門檻。永久失格旗標不能藉補功勳、改階段或 Admin 身分清除。
- 封存要求先明確結束活動、回村或取消預約；不自動解除占用。封存卡片從一般清單移除，養成頁可包含封存卡片查看歷史。接替卡片保留前任 ID 與同帳號關聯，進度、所得、資格重新開始。

## 交易、重試與同步

所有 M4 業務命令先鎖 RequestId，再鎖帳號資料列，最後鎖工作區版本；和既有區域操作共用帳號鎖，避免預約與封存競態。資格／功勳／所得／活動／日誌／去重收據在同一 PostgreSQL 交易提交。資料庫另有一筆有效輪次／活動的部分唯一索引及所得 RequestId 唯一索引。

同 RequestId、卡片與完整命令重試會回傳原成功結果，即使其後餘額已改變也不再寫入；更換 payload 或卡片則拒絕。不同收入命令相加，不用舊總數覆寫。養成命令使用進度版本，更正累積使用金幣版本；兌換在鎖內讀最新餘額。

前端送出前在目前分頁的 `sessionStorage` 保存請求。網路或 5xx 結果不明時保留並停用新業務操作，重新整理後可用原請求確認；明確 4xx 拒絕則保留表單草稿供修改。已提交命令須等畫面同步到回應的工作區版本，才恢復後續按鈕，避免連續操作誤用舊版本。關閉分頁或清除瀏覽器儲存會失去本機待確認請求，因此畫面提示保留頁面；伺服器收據及歷史仍保存。

金額／進度限制在 JavaScript 可精確表示的非負整數範圍 `0..9007199254740991`；所得與兌換必須大於 0。時區先正規化為 IANA；若換日時間遇到時區跳時，採第一個有效分鐘，重複時間採較晚 UTC 時刻。Asia/Taipei 04:00 邊界另有完整日期測試。

Playwright 的 M4 情境：

1. 從畫面建立職業門檻、確認進度、重複保存資格快照；將瀏覽器時間調到未來仍不能提前入場。
2. 雙工作階段看到完整活動；實際提交兌換後刻意中斷回應，重載再用同一 RequestId 確認，只增加一次；兌換至 0、補填時間、結束後同日重新入場。
3. 有占用／活動時封存被拒；重刷、再次達標、永久失格、明確解除占用後封存；接替卡片所得為 0、舊卡保留所得。
4. 兩人同時回報不同所得都保留；累積更正草稿遇到新收入時拒絕，載入最新版本後才能校正。

瀏覽器測試使用 `psql` 在隔離測試庫把指定虛構卡片資格移至昨日 04:00，避免等待實際換日；正式伺服器沒有測試時鐘 HTTP 入口。真正邊界由可注入時鐘的 Domain／API 測試驗證。執行 E2E 時須讓 PostgreSQL client 的 `psql` 位於 PATH，並設定指向可清空測試庫的 `ConnectionStrings__Workspace`；CI 的 PostgreSQL service container 亦執行同套案例。

## 升級與回退

新增 `20260919150349_ProgressionAndActivities`，不重新命名任何既有 migration。新增職業、規則、進度、資格、活動、收入與請求收據資料表；卡片增加封存與前任關聯；階段增加轉換條件；日誌說明長度由 500 擴至 1200。

M3 沒有獨立 schema，因此升級測試以 `ConfigurableData` 邊界建立 M3 舊庫，放入版本 9 的有效占用及版本 4 的自訂值再套用 M4。舊卡片不建立推定的 M4 進度或資格。CI 另保留 M0 舊 ID 升級和空庫重建檢查。

在停止舊網站後備份預覽資料，執行 README 的 M4 `database update`／publish／啟動流程。M4 PR 先以尚未合併的 M3 分支為基底；先合併 M3，再將 M4 PR 改為 `main` 並確認檢查。未自行合併 PR 或部署。

EF `Down` 會移除 M4 表、欄位與去重收據，且把日誌長度縮回 500，既有較長紀錄可能使降版失敗。降 schema 不是無損程式回退；需要回退時先備份並制定資料恢復方案。M3 舊程式不了解封存卡片，不能直接在已有 M4 封存資料的資料庫上回退執行。

第一版仍採單一 Web 實例。Windows 桌面屬 M6；實際職業門檻與遊戲時區由預覽操作核對。原有 npm 開發／測試依賴仍回報 5 項公告（1 moderate、3 high、1 critical）；本次未更換套件版本。
